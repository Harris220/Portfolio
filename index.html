Contexte

Projet personnel · Recherche

Contexte & objectif

Ce projet est né d'une curiosité pour les mécanismes d'attaque distants et leur détection par les solutions de sécurité modernes. L'objectif était de comprendre, du point de vue de l'attaquant, comment fonctionnent les outils de contrôle à distance — pour mieux anticiper leur présence lors d'une analyse forensique ou d'une réponse à incident.

Le développement en Delphi s'est imposé naturellement : le langage compile en binaire natif Win32, dispose d'un accès direct aux API Windows bas niveau, et génère des exécutables sans dépendances — des caractéristiques qui en font un choix classique dans la recherche en sécurité offensive.

// Architecture client-serveur
Agent (cible) <——TCP/IP——> Controller (attaquant)

+ Connexion persistante avec reconnexion automatique
+ Communication chiffrée (XOR / RC4)
+ Obfuscation du binaire pour tests de détection

Fonctionnalités développées

⌨

Keylogger

Capture des frappes clavier via hooks Windows (SetWindowsHookEx). Stockage local avec exfiltration périodique vers le contrôleur.

🖥

Screen Monitor

Capture d'écran à intervalles réguliers avec compression et transmission en temps réel via le canal de commande.

🍪

Vol de cookies

Extraction des cookies navigateurs (Chrome, Firefox) depuis les profils utilisateur via accès au fichier SQLite local.

📁

File Manager

Navigation dans l'arborescence, upload/download de fichiers, exécution de processus à distance.

💻

Remote Shell

Shell interactif (cmd.exe) piped vers le contrôleur avec redirection stdin/stdout/stderr.

🔒

Persistance

DLL Hijacking d'un service Windows afin d'assurer l'exécution automatique du programme lors du démarrage du système.

🔄

Update System

Système de mise à jour à distance permettant le déploiement de nouvelles versions du client sans intervention manuelle.

🎭

RunPE

Étude des techniques d'exécution en mémoire afin d'analyser les mécanismes de détection et d'obfuscation utilisés par les solutions de sécurité modernes.

Tests de détection antivirus

Une partie importante du projet consistait à tester la capacité de détection des solutions AV/EDR, afin de comprendre leurs mécanismes de signature et d'analyse comportementale. Les tests ont été réalisés en environnement isolé (VM sans réseau externe).

// Résultats
Windows Defender → non détecté
Avast Free → non détecté
Malwarebytes → non détecté
Kaspersky → non détecté
Palo Alto WildFire → non détecté

// Observation
les solutions testées n'ont pas détecté l'échantillon dans l'environnement de laboratoire utilisé

Ce travail a permis de comprendre concrètement pourquoi les EDR modernes ne se basent plus uniquement sur les signatures statiques, mais analysent les comportements à l'exécution — une connaissance directement utile pour configurer et interpréter des alertes en environnement de production.

Ce que ce projet m'a appris

Au-delà du code, ce projet a été un cours pratique sur la façon dont les équipes blue team doivent penser. Chaque fonctionnalité développée m'a forcé à me demander : quel artefact ça laisse ? Quelle API Windows utilise-t-on ? Comment un analyste détecterait-il ça dans les logs ?

Résultat : une compréhension bien plus fine des indicateurs de compromission (IOC), des mécanismes de persistance Windows, et de la pertinence des règles de détection dans les SIEM.

Présentation

EpyTodo est un projet Epitech visant à construire une API REST de A à Z en TypeScript. L'objectif : gérer des utilisateurs et leurs tâches (todos) avec un système d'authentification complet — tout en respectant une architecture modulaire et des bonnes pratiques backend.

// Structure du projet
src/
├── config/db.ts // Connexion MySQL
├── index.ts // Entry point Express
├── middleware/
│ ├── auth.ts // Vérification JWT
│ └── notFound.ts // 404 handler
└── routes/
├── auth/auth.ts
├── todos/todos.ts + todos.query.ts
└── user/user.ts + user.query.ts

Base de données MySQL

Deux tables reliées par une clé étrangère : user et todo. Le schéma complet est exporté dans un fichier epytodo.sql versionnés dans le repo.

-- Table user
id INT AUTO_INCREMENT PRIMARY KEY,
email VARCHAR(255) UNIQUE NOT NULL,
password VARCHAR(255) NOT NULL, -- bcrypt hash
name / firstname VARCHAR(255) NOT NULL,
created_at DATETIME DEFAULT CURRENT_TIMESTAMP

-- Table todo
id INT AUTO_INCREMENT PRIMARY KEY,
title / description NOT NULL,
due_time DATETIME NOT NULL,
status ENUM('not started','todo','in progress','done'),
user_id INT → FK vers user(id)

Routes & authentification

POST /register · /login

Inscription avec hash bcrypt, connexion avec vérification et retour d'un token JWT signé.

GET·PUT·DELETE /users/:id

CRUD utilisateur avec vérification du token JWT dans le header Authorization.

CRUD /todos

Création, lecture, mise à jour et suppression des tâches. Accès restreint via middleware auth.

Error middleware

Gestion centralisée des erreurs : 401 (no token), 400 (bad param), 404 (not found), 500 (server error).

// Middleware JWT
const token = req.headers['authorization'];
if (!token) return res.status(401).json({ msg: 'No token, authorization denied' });
jwt.verify(token, process.env.SECRET, (err, decoded) => {
  if (err) return res.status(401).json({ msg: 'Token is not valid' });
  req.user = decoded; next();
});

Ce que ce projet m'a appris

EpyTodo a été ma première expérience complète de backend en TypeScript. La contrainte sur les packages autorisés (pas d'ORM, pas de librairie de validation) m'a forcé à comprendre réellement ce qui se passe entre une requête HTTP et la base de données.

La partie JWT + bcrypt m'a aussi donné une base solide sur les bonnes pratiques de sécurité applicative : ne jamais stocker de mots de passe en clair, valider les inputs, séparer les responsabilités entre routes et queries.

Dataset & objectif

Le dataset contient des enregistrements de trajets ferroviaires : gare de départ/arrivée, heure prévue, heure réelle, et délai en minutes (négatif = avance). L'objectif est de nettoyer ces données et d'en extraire des tendances visuelles exploitables pour un modèle prédictif.

// Colonnes du dataset
date, departure_station, arrival_station,
scheduled_time, actual_time, delay_minutes

// Chargement et exploration initiale
df = pd.read_csv('train_delays.csv')
df.info() # types + nulls
df.describe() # stats descriptives
df.isnull().sum() # valeurs manquantes

Pipeline de nettoyage

Valeurs manquantes

Analyse par colonne via isnull(). Suppression avec dropna() ou imputation selon le taux de nullité.

Doublons

Détection via duplicated() et suppression avec drop_duplicates().

Types & formats

Conversion des colonnes date/heure avec pd.to_datetime() pour activer les opérations temporelles.

Feature Engineering

Extraction du jour de la semaine (dt.dayofweek), catégorisation des retards (à l'heure / léger / majeur).

// Catégorisation des retards
def categorize_delay(minutes):
  if minutes <= 0: return 'on time'
  elif minutes <= 5: return 'slight delay'
  elif minutes <= 20: return 'moderate delay'
  else: return 'major delay'

df['delay_category'] = df['delay_minutes'].apply(categorize_delay)

Visualisations

Après nettoyage, plusieurs visualisations ont été générées pour explorer les tendances : histogramme de distribution des retards, boxplot par gare, heatmap des corrélations, lineplot des retards moyens par jour de la semaine et countplot des catégories de retard.

// Exemples de visualisations
sns.histplot(df['delay_minutes'], bins=30) # distribution
sns.boxplot(x='departure_station', y='delay_minutes', data=df)
sns.heatmap(df.corr(), annot=True) # corrélations
sns.lineplot(x='day_of_week', y='delay_minutes', data=df)
